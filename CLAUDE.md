# CLAUDE.md

## Projekt

Digitale Abhak-Checkliste für Früh- und Spätschicht an der Rezeption (Vorlage: Papier-Aushang „Checkliste neue Rezeption").

- Quellcode in `app/app.js` (+ `app/app.css`): `mount(container, opts)` rendert die App in einen Shadow-Root, `createSpDb(opts)` ist der SharePoint-Speicher. **Nicht `index.html` bearbeiten** – `node tools/build.mjs` erzeugt daraus `index.html` (eigenständig: Mac lokal / claude.ai-Artifact) und `sharepoint/src/webparts/rezeption/app.gen.ts`.
- Speicher-Modi (`opts.mode`): `auto` (claude.ai-DB falls vorhanden, sonst `localStorage` `rz2*` mit Sicherung per File System Access in einen gewählten Ordner), `sharepoint` (JSON-Dateien in der Dokumentbibliothek `RezeptionDaten`: `config/plan.json`, `days/JJJJ-MM/JJJJ-MM-TT.json`; Schreiben per Lesen-Mergen-Schreiben mit ETag/If-Match, Abgleich per Abfrage alle 15 s; Versionsverlauf der Bibliothek = Sicherung). Import einer lokalen Sicherung schreibt in SharePoint und überschreibt vorhandenes Team/PIN nicht.
- SharePoint-Webpart: `sharepoint/` (SPFx 1.23.2, ohne Framework). Bauen: `node tools/build.mjs && cd sharepoint && npm install && npm run build` → `sharepoint/sharepoint/solution/rezeption-checkliste.sppkg` (wird committet). Admin-Anleitung: `sharepoint/ANLEITUNG-ADMIN.md`. Neue Version: `version` in `sharepoint/config/package-solution.json` erhöhen.
- Mac-App: `mac/` (Electron 44.5.1). `main.js` liefert die App über das Schema `rezeption://app/` aus (feste Herkunft → `localStorage` dauerhaft in `~/Library/Application Support/Rezeption`), `preload.js` stellt `window.rezeptionNative` bereit (Sicherungen ohne Rückfrage nach `~/Documents/Rezeption Sicherungen`, Autostart, pdf.js lokal). `app.js` erkennt die Brücke (`NATIVE`). Bauen: `cd mac && npm install && npm run build` → `mac/dist/Rezeption-AppleChip.zip` (Standard nur arm64, der Rezeptions-Mac ist ein M1; `ARCHS=arm64,x64` baut zusätzlich Intel; nicht committet). Ohne Mac: `ELECTRON_ZIP_DIR` (vorab geladene `electron-v44.5.1-darwin-*.zip`, der Downloader scheitert am Proxy der Cloud-Umgebung) und `RCODESIGN` (rcodesign 0.29 für die Ad-hoc-Signatur, sonst starten die Apps auf Apple-Chips nicht). Installationsanleitung: `mac/ANLEITUNG-MAC.md`.
- Monatsplan-Import (Dienstplan › Bearbeiten): liest .pdf (pdf.js 4.4.168 dynamisch von jsDelivr, `opts.pdfjsUrl` überschreibt) und .xlsx (eigener ZIP/XML-Leser, `DecompressionStream`). Aufbau: `OKT | Tag | Vormittags | Uhrzeit | Anmerkung | Nachmittags/Abends | Uhrzeit | Anmerkung`, Namen in den Vormittags-/Nachmittags-Spalten. `findColumns` sucht die Kopfzeile, Zellen werden per Position (PDF: x, Excel: Spalte) zugeordnet. Der Import ersetzt pro Tag Einteilung, `times` (überschreiben Schichtbeginn/-ende via `withRosterTimes`) und `notes` (nur Anzeige); unbekannte Namen werden als Personen angelegt. Monat aus der Kopfzelle (z. B. „OKT“) bzw. dem Dateinamen. pdf.js-Quellen der Reihe nach (`PDFJS_CANDIDATES`): `opts.pdfjsUrl`, Mac-App lokal, `pdfjs/` neben index.html, jsDelivr. `tools/build.mjs` erzeugt `pdfjs/` aus der **Legacy-Fassung** `mac/node_modules/pdfjs-dist/legacy/build` (die moderne braucht `Promise.withResolvers`, fehlt in Safari < 17.4 → Import scheiterte auf dem iPad) (rohe Steuerzeichen als `\uXXXX`, sonst lehnt claude.ai die Datei ab; nicht committet) – die Webversion wird mit `files: {checkin.html, pdfjs/pdf.min.mjs, pdfjs/pdf.worker.min.mjs}` veröffentlicht. Außerhalb der Mac-App läuft pdf.js ohne Worker (`globalThis.pdfjsWorker`), weil claude.ai/SharePoint fremde Worker oft blockieren. Datei-Auswahl über **ein festes Feld `#rzfile` außerhalb von `<main>`** (Knöpfe sind `<label for="rzfile" data-filepick="plan|backup">`): `render()` ersetzt `<main>` komplett, und iPad-Safari zeichnet beim Zurückkehren aus der Dateiauswahl neu, bevor es die Datei übergibt – ein Feld in `<main>` ging dabei verloren. Feld nie `display:none`. Während des Lesens zeigt die Vorschau „Lese … “ (Zeitlimit 45 s). Nach „Übernehmen“ bleibt der Dienstplan im Bearbeiten-Modus auf dem eingelesenen Monat; währenddessen erscheint keine Anmeldemaske.
- Personen ohne Login: Team (`cfg.people`) und Dienstplan (`cfg.roster[datum] = {frueh, spaet, times?, notes?}`) in der Konfiguration. Name antippen = **Einchecken** (Beginn in 15-Min-Schritten, Rolle Früh/Spät/Sonstiges – Schlüssel bleibt `aushilfe`, optionale Notiz); aktive Person pro Gerät in `rz2who` gilt nur, solange sie heute eingecheckt ist. `by` in Haken/Notizen/Logs = Personen-ID.
- Zeiterfassung: `days/<datum>.time = { <id>: { pid, role, in, out|null, pause|null, note?, at, orig?, editedAt? } }` (Tag des Beginns, `persistTime`). Auschecken über den Knopf im Kopf (Ende + Pause, Vorschlag gesetzliche Mindestpause), vergessenes Auschecken wird beim nächsten Einchecken nachgefragt. Anmeldemaske (`#picker.login`, bildschirmfüllend) erscheint, sobald niemand eingecheckt ist (nicht in Verwaltung/PIN-Bereichen); „Neue Person“ legt ohne PIN an (`addPersonAndPick`). „Nur ansehen“ (`state.viewOnly`) sperrt Schicht und Erstattung (Capture-Listener `blockViewOnly`, Leiste `#vobar`) bis zum nächsten Einchecken. Mehrere Anwesende: Anwesend-Leiste `#presence` im Kopf (`presentPeople`, Chip antippen = aktiv, „+“ = weitere Person, `ensureActive` übernimmt nach dem Auschecken). Letzte Person checkt aus → Feierabend-Bildschirm (`localStorage` `rz2bye`, gerätebezogen, nicht in der Sicherung) bis zur nächsten Anmeldung bzw. zum nächsten Tag; sonst Hinweis „Schönen Feierabend“ (`toast`). Ohne eingecheckte Person keine Pflicht-Erinnerung. Pflichtpunkte bleiben planbasiert (Erinnerung 30 Min vor geplantem Ende). Tab „Zeiten“: eigene Zeiten per Namenswahl, alle + Korrektur (`orig` hält den Ursprungswert) + Export nur mit Leitungs-PIN. Webversion = claude.ai-Artifact https://claude.ai/artifact/1nFKWDs2ppiZ4Hd99g5WB2 (Fähigkeiten `db`, `user`, `downloads`; eigene Daten, kein Abgleich mit der Mac-App; Sicherung der Mac-App lässt sich unter Verwaltung › Datenspeicher übernehmen). Downloads laufen über `offerFile` (claude.ai `downloads.save`, sonst `<a download>`). Export ohne Fremdbibliothek: `buildXlsx` (ZIP stored + SpreadsheetML), `buildPdf` (A4 quer, Helvetica/WinAnsi); Mac-App speichert über `rz:saveExport` mit „Sichern unter“.
- Reiter „Check-ins“ (intern `erstattung`) = Check-in-Erstattung (Tagesprüfung USC/Wellpass/Wellhub/Hansefit gegen den Playtomic-Export, Wallet buchen, Regeln & Preise, Hansefit-Liste). Eigenständige Seite `app/checkin.html` (Quelle; `tools/build.mjs` kopiert sie nach `checkin.html`), im iframe in `#ciwrap` geladen und nur ein-/ausgeblendet, damit Prüfergebnisse beim Reiterwechsel bleiben. Nur sichtbar mit `opts.checkinUrl` (index.html: ja, SharePoint: nein). Gestaltung wie die App (gleiche Tokens/Schriften, Karten, Umschalter, Pills; keine Emojis). Brücke per `postMessage`: Seite → App `rz-download` (App speichert über `offerFile`) und `rz-status` (Reiter zeigt „n offen“), App → Seite `rz-user` (eingecheckte Person = „Bearbeitet von“, sonst Kürzel-Feld) und `rz-theme`. Fahrplan-Punkte mit „Check-in“ im Text bekommen den Knopf „Check-ins ›“ (`data-goview`). Daten der Seite in `localStorage` `cir.*` (pro Gerät; die Mac-Sicherung enthält sie). Keine `prompt()`/`confirm()` (Electron kennt kein `prompt`), stattdessen `ask()`. SheetJS 0.18.5: Mac-App lokal aus `vendor/` (devDependency `xlsx`), sonst cdnjs. Tagesprüfung in drei Gruppen (`groupOf`: zu entscheiden / wird erstattet / keine Erstattung) mit Freigeben/Ablehnen/Zurücknehmen; Benefit = Anbieter des Check-ins (`BENEFIT`, farbige Marke `bpill`). Wallet buchen als Schritte 1 Nutzer suchen · 2 Benefit im Profil prüfen (Pflicht: `benefitOk`, ohne Bestätigung kein Buchen; „Fehlt“ lehnt mit Grund ab – der Export hat keine Benefit-Spalte, daher manuell) · 3 Betrag · 4 Notiz „Match TT.MM.JJJJ“ (Datum der Buchung) · 5 Fertig (Tasten 1/3/4 kopieren, J/N Benefit), „Ablehnen …“ mit optionalem Grund (`rejectReason`, steht in der Dokumentation), Abschlusskarte „Alles gebucht“. Testdaten (erfundener Prüftag 23.10.2026, alle Fälle mit erwartetem Ergebnis): `testdaten/checkins/`.
- Verwaltung, Aufgaben-Plan und Dienstplan-Bearbeitung hinter Leitungs-PIN (`cfg.adminPin`, FNV-Hash; `"off"` = PIN deaktiviert, `isUnlocked()` dann immer wahr) – nur Schutz vor versehentlichen Änderungen, keine echte Zugriffskontrolle.
- `DEFAULT_PLAN` im Script ist der Ausgangsplan (Aushang). Unter Verwaltung › Aufgaben-Plan lässt er sich ändern; welcher Plan gilt, entscheidet `resolvePlan`: Tagesanpassung (`days/<datum>.plan`) > Wochentag-Vorlage (`config/plan.weekday["0"-"6"]`, 0 = Sonntag) > Standard (`config/plan.base`) > `DEFAULT_PLAN`. Alles aus der DB läuft durch `normalizePlan`. Der Editor bearbeitet wahlweise den Tag oder die Gruppen Mo–Fr / Sa+So (`state.edScope`, `GROUPS`; Speichern schreibt die Wochentag-Vorlagen aller Tage der Gruppe). Abschnittszeiten ziehen Schichtbeginn/-ende mit (`fitShift`), neue Abschnitte starten am Ende des letzten. Achtung: `normTime` (Uhrzeit-Text) und `normTimes` (Zeiterfassung) nicht verwechseln.
- Item-IDs (`f_*`, `s_*`, neue `*_x…`) sind Schlüssel für die Haken – nie umbenennen. Optionale Punkte (`optional`) lassen sich auf „entfällt“ setzen (`s: "na"`): dann durchgestrichen, Haken gesperrt, der Knopf heißt „rückgängig“. Daueraufgaben (`always`) haben eine Art `kind`: `rhythm` (beliebig oft abhakbar, Zähler, `every` Minuten bis „fällig“), `confirm` (Pflicht: einmal pro Schicht bestätigen; in den letzten 30 Min. der Schicht erinnert ein Fenster, die Namenswahl der Spätschicht warnt vor Unbestätigtem der Frühschicht), `hint` (nur Anzeige). Bestätigungen und Haken sind Einträge in `logs`. Pläne ohne `kind` werden in `normalizePlan` zugeordnet.
- Ansichten: Schicht (eine Ansicht für Früh/Spät, `state.shiftSel` null = laufende Schicht; links Fahrplan: chronologische Abschnitte, erledigte als eine Zeile, aktueller hervorgehoben; rechts Immer im Blick, Dienst & Übergabe), Dienstplan (Monatskalender Mo–So, Bearbeiten per Tag-Fenster inkl. Notiz pro Schicht = `roster[datum].notes`, orange; Feld „Hervorheben“ markiert Tage per Wortanfang-Treffer in Namen und Notizen, `applyRosterHi` direkt im DOM), Zeiten, Verwaltung (Team, Aufgaben-Plan, Monatsstatistik, Datensicherung, PIN; alles hinter der Leitungs-PIN). Im Querformat ≥ 900 px passt alles auf einen Bildschirm, nur Karten scrollen intern. Breite der rechten Spalte und Höhe von „Dienst & Übergabe“ (Trennlinien `data-split="side"|"hand"` ziehen oder Pfeiltasten, Doppelklick = Standard) sowie Fahrplan-Spalten (Auto/1/2) gelten pro eingecheckter Person: `localStorage` `rz2layout` = `{ <personId>|"_": { side, cols, hand|null } }`.
- Datenmodell: ein Dokument pro Tag `days/YYYY-MM-DD` = `{ month: "YYYY-MM", checks: { <itemId>: { s: "done"|"na", by: <userId>, at: <ISO> } | null }, notes: { frueh|spaet: { text, by, at, important? } }, read: { <Empfänger-Schicht>: { by, at, noteAt } }, logs: { frueh|spaet: { <alwaysId>: { <key>: { at, by } | null } } }, plan?: Plan|null }`. Die Frühschicht liest die Spät-Notiz vom Vortag. Übergabe „Gelesen“ speichert die lesende Schicht in ihrem Tagesdokument (`read.frueh` bzw. `read.spaet`); gilt nur, solange `noteAt` dem `at` der Notiz entspricht (Änderung → wieder ungelesen). „Wichtig“ (`important`) öffnet nach dem Einchecken ein Fenster (`maybeShowHandover`, Sonstiges → laufende Schicht).

## Courtside (`courtside/`)

Eigene Web-App (PWA, kein Build) für Turniere in Padel (Schwerpunkt), Pickleball und Tennis. Unabhängig von der Checkliste. Netlify-Basisverzeichnis ist `courtside/` (`netlify.toml`).

Live unter https://courtside-turniere.netlify.app (Netlify-Site-ID `5bae8eb4-f745-4e26-83f0-40e6d65e26ac`, nur die Produktion ist öffentlich, Vorschauen brauchen Netlify-Login). Neu veröffentlichen: Netlify-Connector `deploy-site` mit dieser `siteId`, den gelieferten Befehl im Ordner `courtside/` ausführen. Die Cloud-Umgebung darf Netlify nicht erreichen; der Befehl läuft deshalb in einer Sitzung auf dem Raspberry Pi des Nutzers.

- `public/` – die App. `engine.js` ist reine Logik ohne DOM: vier Modi (Americano, Mexicano, King of the Court, Team-Turnier) auf zwei Motoren (`rotation`, `ladder`), Spielstärke (`LEVELS`, Playtomic 0–7 hat Vorrang), Teambildung (`buildTeams`: `similar` = gut mit gut, `balanced` = gut mit schwächer), Tabellen und `next()` = „Was kommt als Nächstes“.
- `public/app.js` – Oberfläche, Speicher (`localStorage` `courtside.v1`, Spieler-Links in `courtside.me`), Undo per Snapshot, Timer, Navigation mit History-API. Turniere mit `status: 'draft'` sind offene Online-Anmeldungen; erst beim Start entsteht daraus ein Engine-Turnier.
- Spielerseite: `?anmeldung=<eventId>` (gemeinsamer Link), persönlicher Link zusätzlich `&ich=<playerId>#k=<token>`.
- `netlify/functions/api/` – Anmelde-API unter `/api/*`: `core.mts` ist die Logik mit austauschbarem Speicher, `api.mts` bindet Netlify Blobs an (Region `eu-central-1`). Jede Anmeldung ist ein eigener Blob-Schlüssel (`e/<id>/p/<pid>`), Admin- und Spieler-Schlüssel liegen nur als SHA-256 vor.
- `public/index.html` – CSS mit zwei Designsprachen über `html[data-platform="ios"|"android"]`. Spielfelder im echten Seitenverhältnis (Padel 20 × 10 m).
- `public/sw.js` – Offline-Cache, `/api/*` geht immer ans Netz. Bei Änderungen an Dateien `CACHE` hochzählen.
- `public/vendor/qrcode.js` – QR-Code-Generator (Kazuhiko Arase, MIT), unverändert.

## Testen

Checkliste: kein automatisiertes Test-Setup. Lokal: `index.html` im Browser öffnen. SharePoint ohne Tenant: `node tools/sp-mock.mjs 8899` startet einen Nachbau der genutzten REST-Endpunkte und liefert `http://localhost:8899/sites/rez/test.html` (App im SharePoint-Modus, Abgleich jede Sekunde). `/__dump` zeigt die gespeicherten Dateien, `/__fail?n=3` lässt die nächsten Schreibzugriffe scheitern. Mit `PDFJS_DIR=<pdfjs-dist>/build` liefert der Nachbau pdf.js lokal aus (für PDF-Import-Tests ohne Internet).

Courtside (im Ordner `courtside/`): `npm test` prüft Engine und API. `npm run dev` startet `dev/server.mjs` auf Port 8888: liefert `public/` aus und beantwortet `/api/*` mit einem Speicher im Arbeitsspeicher, so lässt sich die Online-Anmeldung lokal mit mehreren Browserfenstern durchspielen.
