# CLAUDE.md

## Projekt

Digitale Abhak-Checkliste für Früh- und Spätschicht an der Rezeption (Vorlage: Papier-Aushang „Checkliste neue Rezeption").

- Quellcode in `app/app.js` (+ `app/app.css`): `mount(container, opts)` rendert die App in einen Shadow-Root, `createSpDb(opts)` ist der SharePoint-Speicher. **Nicht `index.html` bearbeiten** – `node tools/build.mjs` erzeugt daraus `index.html` (eigenständig: Mac lokal / claude.ai-Artifact) und `sharepoint/src/webparts/rezeption/app.gen.ts`.
- Speicher-Modi (`opts.mode`): `auto` (claude.ai-DB falls vorhanden, sonst `localStorage` `rz2*` mit Sicherung per File System Access in einen gewählten Ordner), `sharepoint` (JSON-Dateien in der Dokumentbibliothek `RezeptionDaten`: `config/plan.json`, `days/JJJJ-MM/JJJJ-MM-TT.json`; Schreiben per Lesen-Mergen-Schreiben mit ETag/If-Match, Abgleich per Abfrage alle 15 s; Versionsverlauf der Bibliothek = Sicherung). Import einer lokalen Sicherung schreibt in SharePoint und überschreibt vorhandenes Team/PIN nicht.
- SharePoint-Webpart: `sharepoint/` (SPFx 1.23.2, ohne Framework). Bauen: `node tools/build.mjs && cd sharepoint && npm install && npm run build` → `sharepoint/sharepoint/solution/rezeption-checkliste.sppkg` (wird committet). Admin-Anleitung: `sharepoint/ANLEITUNG-ADMIN.md`. Neue Version: `version` in `sharepoint/config/package-solution.json` erhöhen.
- Mac-App: `mac/` (Electron 44.5.1). `main.js` liefert die App über das Schema `rezeption://app/` aus (feste Herkunft → `localStorage` dauerhaft in `~/Library/Application Support/Rezeption`), `preload.js` stellt `window.rezeptionNative` bereit (Sicherungen ohne Rückfrage nach `~/Documents/Rezeption Sicherungen`, Autostart, pdf.js lokal). `app.js` erkennt die Brücke (`NATIVE`). Bauen: `cd mac && npm install && npm run build` → `mac/dist/Rezeption-AppleChip.zip` (Standard nur arm64, der Rezeptions-Mac ist ein M1; `ARCHS=arm64,x64` baut zusätzlich Intel; nicht committet). Ohne Mac: `ELECTRON_ZIP_DIR` (vorab geladene `electron-v44.5.1-darwin-*.zip`, der Downloader scheitert am Proxy der Cloud-Umgebung) und `RCODESIGN` (rcodesign 0.29 für die Ad-hoc-Signatur, sonst starten die Apps auf Apple-Chips nicht). Installationsanleitung: `mac/ANLEITUNG-MAC.md`.
- Monatsplan-Import (Dienstplan › Bearbeiten): liest .pdf (pdf.js 4.4.168 dynamisch, `opts.pdfjsUrl` überschreibt) und .xlsx (eigener ZIP/XML-Leser, `DecompressionStream`). Aufbau: `OKT | Tag | Vormittags | Uhrzeit | Anmerkung | Nachmittags/Abends | Uhrzeit | Anmerkung`, Namen in den Vormittags-/Nachmittags-Spalten. `findColumns` sucht die Kopfzeile, Zellen werden per Position (PDF: x, Excel: Spalte) zugeordnet. Der Import ersetzt pro Tag Einteilung, `times` (überschreiben Schichtbeginn/-ende via `withRosterTimes`) und `notes` (nur Anzeige); unbekannte Namen werden als Personen angelegt. Monat aus der Kopfzelle (z. B. „OKT“) bzw. dem Dateinamen. pdf.js-Quellen der Reihe nach (`PDFJS_CANDIDATES`): `opts.pdfjsUrl`, Mac-App lokal, `pdfjs/` neben index.html, jsDelivr **nur im SharePoint-Modus** (dort gibt es keine eigene Kopie; Mac-App und Webversion rufen keine fremden Server ab). `tools/build.mjs` erzeugt `pdfjs/` aus der **Legacy-Fassung** `mac/node_modules/pdfjs-dist/legacy/build` (die moderne braucht `Promise.withResolvers`, fehlt in Safari < 17.4 → Import scheiterte auf dem iPad) (rohe Steuerzeichen als `\uXXXX`, sonst lehnt claude.ai die Datei ab – gilt auch für `vendor/xlsx.full.min.js`; beides nicht committet) – die Webversion wird mit `files: {checkin.html, pdfjs/pdf.min.mjs, pdfjs/pdf.worker.min.mjs, vendor/xlsx.full.min.js}` veröffentlicht. - Konfiguration enthält zusätzlich `features: { checkins }` (fehlt in alten Sicherungen → aus).
- Verwaltung, Aufgaben-Plan und Dienstplan-Bearbeitung hinter Leitungs-PIN (`cfg.adminPin`; `"off"` = PIN deaktiviert, `isUnlocked()` dann immer wahr). Ab 1.17 Hash `p2:<salz>:<runden>:<hash>` (PBKDF2-SHA256, `pinHashSecure`/`pinMatches`); alte `f1:`-FNV-Hashes gelten weiter und werden beim nächsten richtigen Entsperren umgestellt. Nach 5 Fehlversuchen Sperre ab 1 Min., verdoppelt bis 30 Min. (`localStorage` `rz2pinlock`, gerätebezogen). Bleibt ein Schutz gegen Neugier/Versehen, keine echte Zugriffskontrolle.
- Sicherungen: `backupPayload()` (async) liefert `version: 1` (Klartext, `data` = localStorage-Schlüssel `rz2*` ohne `DEVICE_KEYS` und `cir.*`) oder mit `cfg.backupKey` `version: 2` = `{ enc: { alg, key, iv, ct, keys: { pw, code } } }`: RSA-OAEP-3072 (öffentlicher Schlüssel in `cfg.backupKey.pub`) verschlüsselt pro Sicherung einen AES-256-GCM-Schlüssel; der private Schlüssel liegt mit PBKDF2 (310 000 Runden) aus dem Leitungs-Passwort und aus dem Wiederherstellungscode verpackt in jeder Datei – automatische Sicherung ohne Passwort, Öffnen auf jedem Gerät mit Passwort oder Code (`createBackupKey`, `encryptBackup`, `decryptBackup`). Einrichten unter Verwaltung › Datensicherung (`setupEncryption`, Code nur einmal angezeigt, `state.encCode`); Import erkennt `version: 2` und fragt im Fenster `decrypt` (`state.pendingImport`, `applyImport` für Klartext). Alte Klartext-Sicherungen lassen sich weiter einspielen.
- Alte Daten löschen (Verwaltung › System, nur lokal): `cleanupScan`/`runCleanup` – Protokoll/Übergaben/„Gelesen“ nach 3 Monaten, Dienstplan nach 1 Jahr, Arbeitszeiten ab 01.01. des vorletzten Jahres; Tage ohne verbleibende Einträge werden entfernt, `snap` bleibt. Nachweis ohne Inhalte in `rz2meta.cleanups`. Die Check-in-Seite entfernt ihren Prüf-Fortschritt (`cir.progress.v1`) älter als 3 Monate selbst beim Start.
- `DEFAULT_PLAN` im Script ist der Ausgangsplan (Aushang). Unter Verwaltung › Aufgaben-Plan lässt er sich ändern; welcher Plan gilt, entscheidet `resolvePlan`: Tagesanpassung (`days/<datum>.plan`) > Wochentag-Vorlage (`config/plan.weekday["0"-"6"]`, 0 = Sonntag) > Standard (`config/plan.base`) > `DEFAULT_PLAN`. Alles aus der DB läuft durch `normalizePlan` (Aufgaben dürfen `remind: "HH:MM"` tragen). **Aufgaben-Plan-Editor (ab 1.12):** ein Plan für alle Tage in `cfg.master = { plan, we }` – `plan` mit allen Abschnitten/Aufgaben und den Mo–Fr-Zeiten, `we` mit den Sa+So-Zeiten (`we.frueh|spaet = { start, end }`, `we.phases[<phaseId>] = { from, to }`, `we.remind[<itemId>]`). Fehlt `master`, baut `masterFromTemplates` ihn aus den bisherigen Vorlagen (Montag = Mo–Fr, Samstag = Sa+So, Aufgaben nur eines Tages kommen dazu). Jede Änderung läuft über `editMaster` und gilt sofort: speichert `master`, `materialize` erzeugt daraus die Vorlagen `weekday["0"-"6"]` (Sa/So mit Wochenend-Zeiten) und `base` – `resolvePlan` bleibt unverändert, ältere Versionen lesen den Plan weiter; danach `refreshTodaySnap`. Bedienung: Schicht wählen, Abschnitte aufklappen (`state.edOpen`), „+ Aufgabe“ = Eingabezeile (`state.edAdd`, Enter fügt hinzu, bleibt offen), Antippen öffnet das Fenster (`state.edPop`: item/phase/shift/always, `submitEdPop`, Löschen mit Nachfrage), Sortieren am Griff ⋮⋮ (`startSort`, Pointer-Events auf Dokument-Ebene, weil das Umhängen der Zeile den Pointer-Capture beendet). Uhrzeiten als Textfeld HH:MM (`normTime`). Tagesanpassungen (`days/<datum>.plan`) legt der Editor nicht mehr an, vorhandene gelten weiter. Abschnittszeiten ziehen Schichtbeginn/-ende mit (`fitShift`). **Erinnerungs-Popups:** Aufgaben mit `remind` öffnen ab dieser Uhrzeit ein Fenster (`taskRemTarget`/`state.taskRem`, nur heute, laufende Schicht, eingecheckt, noch offen – mit `remindAlways: true` auch, wenn schon erledigt: Fenster „Zur Sicherheit“ mit „Kontrolliert“); „Erledigt“ hakt ab, „In 10 Minuten“ bzw. „Kontrolliert“ merkt sich `localStorage` `rz2taskrem` (gerätebezogen, Kontrolliert = für heute); im Fahrplan Glocke mit Uhrzeit (`.remtag`). Achtung: `normTime` (Uhrzeit-Text) und `normTimes` (Zeiterfassung) nicht verwechseln.
- Item-IDs (`f_*`, `s_*`, neue `*_x…`) sind Schlüssel für die Haken – nie umbenennen. Optionale Punkte (`optional`) lassen sich auf „entfällt“ setzen (`s: "na"`): dann durchgestrichen, Haken gesperrt, der Knopf heißt „rückgängig“. Daueraufgaben (`always`) haben eine Art `kind`: `rhythm` (beliebig oft abhakbar, Zähler, `every` Minuten bis „fällig“), `confirm` (Pflicht: einmal pro Schicht bestätigen; in den letzten 30 Min. der Schicht erinnert ein Fenster, die Namenswahl der Spätschicht warnt vor Unbestätigtem der Frühschicht), `hint` (nur Anzeige). Bestätigungen und Haken sind Einträge in `logs`. Pläne ohne `kind` werden in `normalizePlan` zugeordnet.
- Ansichten: Schicht (eine Ansicht für Früh/Spät, `state.shiftSel` null = laufende Schicht; wer als Früh oder Spät eingecheckt ist, sieht nur die eigene Schicht ohne Umschalter – `lockedShift()`; links Fahrplan einspaltig: nur laufende und überfällige Abschnitte aufgeklappt, erledigte und spätere als eine Zeile zum Aufklappen (`state.expanded`); rechts Immer im Blick – nur fällige Rundgänge und offene Pflicht sichtbar, der Rest in aufklappbaren Zeilen (`state.sideOpen`, `data-sideopen`) – sowie Dienst & Übergabe; die eigene Übergabe wird im Fenster geschrieben (`state.notePop`, `saveNote`; nur „Wichtig“ geändert → Zeitstempel bleibt)), Dienstplan (Monatskalender Mo–So, Bearbeiten per Tag-Fenster inkl. Notiz pro Schicht = `roster[datum].notes`, orange; Feld „Hervorheben“ markiert Tage per Wortanfang-Treffer in Namen und Notizen, `applyRosterHi` direkt im DOM), Zeiten, Verwaltung (hinter der Leitungs-PIN; eine Liste mit Statuszeile in drei Gruppen – Planung: Aufgaben-Plan, Dienstplan, Team · Auswertung: Monatsstatistik, Arbeitszeiten aller (`open-times`) · System: Datensicherung, Check-ins-Schalter, Leitungs-PIN; Team, Datensicherung und PIN öffnen ein Fenster `state.adminPop`, Status aus `backupStatus()`). Im Querformat ≥ 900 px passt alles auf einen Bildschirm, nur Karten scrollen intern. Breite der rechten Spalte und Höhe von „Dienst & Übergabe“ (Trennlinien `data-split="side"|"hand"` ziehen oder Pfeiltasten, Doppelklick = Standard) gelten pro eingecheckter Person: `localStorage` `rz2layout` = `{ <personId>|"_": { side, hand|null } }` (ein altes `cols` wird ignoriert).
- Schriften: Barlow 400/500/600 und Barlow Condensed 600/700 (latin, woff2 aus `@fontsource` 5.3.0) liegen in `app/fonts/` mit den Lizenztexten (SIL OFL 1.1). `tools/build.mjs` bettet sie als data:-URI in den Kopf von `index.html` und `checkin.html` ein (`@font-face` wirkt nicht im Shadow-Root; claude.ai lädt Stylesheets nur von Google Fonts). Keine Google Fonts mehr – keine IP-Übertragung an Google. Die Mac-App liefert die Lizenztexte unter `app/fonts/` mit. SharePoint lädt keine Schriften (Fallback `Arial Narrow`/Systemschrift).
- Unterlagen: `README.md` (Überblick), `ENTWICKLUNG.md` (Bauen, Testen, Regeln), `CHANGELOG.md` (bei jeder Versionserhöhung oben einen Eintrag ergänzen), `sharepoint/README.md`. Node 22 laut `.nvmrc`. `.gitignore` schließt Sicherungen und Exporte aus – echte Daten nie committen; die Webversion enthält nur erfundene Testdaten.
- Plan-Stand pro Tag (`snap`): `persistDay` schreibt bei jedem Schreibvorgang am angezeigten Tag den gültigen Plan als `days/<datum>.snap` mit (heute immer aktualisiert, vergangene Tage nur, wenn noch keiner da ist; nicht bei Tagesanpassung `plan`). `resolvePlan(date, dayPlan, raw, snap)`: Tagesanpassung > `snap` (nur für Tage vor heute, Quelle „Stand vom Tag“) > Wochentag-Vorlage > Standard. Nach Vorlagen-Änderungen zieht `refreshTodaySnap` den heutigen Stand nach. `migrateSnaps` hält beim ersten Start (lokal, `rz2meta.snapV1`) vergangene Tage mit Einträgen einmalig fest. Monatsdaten (`state.month`) tragen `snap` mit.
- Datenmodell: ein Dokument pro Tag `days/YYYY-MM-DD` = `{ month: "YYYY-MM", checks: { <itemId>: { s: "done"|"na", by: <userId>, at: <ISO> } | null }, notes: { frueh|spaet: { text, by, at, important? } }, read: { <Empfänger-Schicht>: { by, at, noteAt, reply? } }, logs: { frueh|spaet: { <alwaysId>: { <key>: { at, by } | null } } }, plan?: Plan|null, snap?: Plan }`. Die Frühschicht liest die Spät-Notiz vom Vortag. Übergabe „Gelesen“ speichert die lesende Schicht in ihrem Tagesdokument (`read.frueh` bzw. `read.spaet`); gilt nur, solange `noteAt` dem `at` der Notiz entspricht (Änderung → wieder ungelesen). „Wichtig“ (`important`) färbt Fenster und Leiste rot; das Fenster nach dem Einchecken kommt immer (`maybeShowHandover`, Sonstiges → laufende Schicht).

## Courtside (`courtside/`)

Eigene Web-App (PWA, kein Build) für Turniere in Padel (Schwerpunkt), Pickleball und Tennis. Unabhängig von der Checkliste. Netlify-Basisverzeichnis ist `courtside/` (`netlify.toml`).

Live unter https://courtside-turniere.netlify.app (Netlify-Site-ID `5bae8eb4-f745-4e26-83f0-40e6d65e26ac`, nur die Produktion ist öffentlich, Vorschauen brauchen Netlify-Login). Neu veröffentlichen: Netlify-Connector `deploy-site` mit dieser `siteId`, den gelieferten Befehl im Ordner `courtside/` ausführen. Die Cloud-Umgebung darf Netlify nicht erreichen; der Befehl läuft deshalb in einer Sitzung auf dem Raspberry Pi des Nutzers.

- `public/` – die App. `engine.js` ist reine Logik ohne DOM: vier Modi (Americano, Mexicano, King of the Court, Team-Turnier) auf zwei Motoren (`rotation`, `ladder`), Spielstärke (`LEVELS`, Playtomic 0–7 hat Vorrang), Teambildung (`buildTeams`: `similar` = gut mit gut, `balanced` = gut mit schwächer), Tabellen und `next()` = „Was kommt als Nächstes“.
- `public/app.js` – Oberfläche, Speicher (`localStorage` `courtside.v1`, Spieler-Links in `courtside.me`), Undo per Snapshot, Timer, Navigation mit History-API. Turniere mit `status: 'draft'` sind offene Online-Anmeldungen; erst beim Start entsteht daraus ein Engine-Turnier.
- Spielerseite: `?anmeldung=<eventId>` (gemeinsamer Link), persönlicher Link zusätzlich `&ich=<playerId>#k=<token>`.
- `netlify/functions/api/` – Anmelde-API unter `/api/*`: `core.mts` ist die Logik mit austauschbarem Speicher, `api.mts` bindet Netlify Blobs an (Region `eu-central-1`). Jede Anmeldung ist ein eigener Blob-Schlüssel (`e/<id>/p/<pid>`), Admin- und Spieler-Schlüssel liegen nur als SHA-256 vor.
- `public/index.html` – CSS mit zwei Designsprachen über `html[data-platform="ios"|"android"]`. Spielfelder im echten Seitenverhältnis (Padel 20 × 10 m).
- `public/sw.js` – Offline-Cache, `/api/*` geht immer ans Netz. Bei Änderungen an Dateien `CACHE` hochzählen.
- `public/vendor/qrcode.js` – QR-Code-Generator (Kazuhiko Arase, MIT), unverändert.

## Live Karten (`atlas/`)

Eigene Web-App (PWA, kein Build): freie Live-Daten ohne Registrierung/API-Key auf einer Karte (eigener Nachbau einer OSINT-Lagekarte, ohne Paywall). Netlify-Basisverzeichnis `atlas/`. ## Testen

Checkliste: kein automatisiertes Test-Setup. Lokal: `index.html` im Browser öffnen. SharePoint ohne Tenant: `node tools/sp-mock.mjs 8899` startet einen Nachbau der genutzten REST-Endpunkte und liefert `http://localhost:8899/sites/rez/test.html` (App im SharePoint-Modus, Abgleich jede Sekunde). `/__dump` zeigt die gespeicherten Dateien, `/__fail?n=3` lässt die nächsten Schreibzugriffe scheitern. Mit `PDFJS_DIR=<pdfjs-dist>/build` liefert der Nachbau pdf.js lokal aus (für PDF-Import-Tests ohne Internet).

Courtside (im Ordner `courtside/`): `npm test` prüft Engine und API. `npm run dev` startet `dev/server.mjs` auf Port 8888: liefert `public/` aus und beantwortet `/api/*` mit einem Speicher im Arbeitsspeicher, so lässt sich die Online-Anmeldung lokal mit mehreren Browserfenstern durchspielen.

Live Karten (im Ordner `atlas/`): `npm test` prüft Normalisierung und Proxy. `npm run dev` startet `dev/server.mjs` auf Port 8890 mit echten Quellen, `npm run dev:mock` mit erfundenen Daten (`dev/mock.mjs`, ohne Internet). `npm run probe` prüft die Erreichbarkeit aller Quellen.
